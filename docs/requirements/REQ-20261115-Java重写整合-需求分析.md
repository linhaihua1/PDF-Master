# 需求分析：PDF 工具箱 Java 重写与整合（PdfKit Desktop）

| 项 | 内容 |
|---|---|
| 需求编号 | REQ-20261115-PDFKIT |
| 版本 | **v1.1（定稿）** — v1.0 完善稿 + 四项决策已闭环 |
| 日期 | 2026-11-15 |
| 原始需求 | 使用 Java 语言重新编写这三个工程的代码，将使用功能整合后成为一个新的项目，新项目运行方式为在 Windows 系统中运行的 exe 文件包 |
| 分析依据 | `engines/` 三份源码快照 + `integration/registry/capabilities.json`（124 项能力实测清单） |
| 结论 | **需求成立，但"全部重写"不成立**。按 90 项复用 + 17 项新建执行；首发取 P0 六十项，先用内嵌 Stirling 出包，约 80 人日（单人 4 个月） |

---

## 0. 一句话结论

**把"重写三个工程"改成"用 Java 重建一个桌面产品"**：目标能力 107 项，首发交付 P0 60 项，其中 90 项（首发覆盖 45 项）由 Java 生态已有实现承接，17 项中 3 项为本项目自研；交付形态为 `jpackage` 生成的 Windows 安装包（内含裁剪 JRE），免装 Java、双击即用。

### 0.1 已确认决策（2026-11-15 定稿，后续变更需走需求变更单）

| # | 决策项 | 结论 | 连带影响 |
|---|---|---|---|
| **D-1** | 使用性质 | **自用 / 内部工具** | ToolKnit 的 PolyForm NC 在非商业内部使用下可用；PDFPatcher 的 AGPL 义务降为「团队内使用者可获取源码」，但仍**不得对外分发二进制而不给源码**；不触发「收益千分之一捐赠」条款 |
| **D-2** | 首发功能范围 | **P0 核心 60 项** | 剔除 PDF转视频、CBZ/EPUB、矢量图互转、可视化编辑器（编辑器列为 P1，首发不做） |
| **D-3** | 起步架构 | **先内嵌 Stirling 快速出包** | 2–3 周拿到可双击运行的 exe；体积 ~320 MB、冷启动 8–15 s 为**已知可接受代价**；阶段二再剥离 Spring 瘦身 |
| **D-4** | Office → PDF | **调系统已装 Office（COM/JNA）** | 安装包零增量；无 Office 的机器给出明确提示，不静默失败，不随包附 LibreOffice |

**决策带来的范围冻结**（v1.1 起不再讨论）：
- 不做跨平台首发、不做账号体系、不做云端
- 不承接 ToolKnit 39 个非 PDF 模块
- 不做 AI 增强转 Markdown 的在线模型接入（P2 且默认关闭）
- Office→PDF 不内置 LibreOffice

三个必须先纠正的认知偏差：

| 原始表述 | 事实 | 处置 |
|---|---|---|
| "重新编写这三个工程" | Stirling-PDF **本身就是 Java**（270 个 .java，Spring Boot 4.1.2 / Java 25） | 不重写，**复用 + 裁剪 Spring** |
| "整合三个工程" | ToolKnit 共 **56 个功能模块**，PDF 只占 17 个，其余是音频/图片/AI/计算器 | 范围必须锁定 PDF，否则工期翻三倍 |
| "exe 文件包" | Java 无原生 exe，需 `jpackage` 内置 JRE | 可行，但分「安装包」与「绿色目录」两种形态，体积差 1 倍 |

## 1. 【业务全景图】

一个**离线优先、免安装 JDK、双击即用**的 Windows PDF 工作台：把原本分散在「Java Web 服务（Stirling）」「.NET 桌面工具（PDFPatcher）」「Electron/Tauri 前端工具（ToolKnit）」三套技术栈里的 107 项 PDF 能力，收进一个 Java 单体程序，用同一套文件选择、参数配置、任务队列、产物保存交互完成操作。

**核心价值**：用户不再需要①启动 Java 服务并开浏览器 ②装 .NET 运行时 ③为了合并两个 PDF 上传到第三方网站。所有处理在本机完成，不上传、不联网、不留痕。

**非目标**（明确排除，避免范围蔓延）：
- 不做多人协作 / 账号体系 / 云端同步
- 不做 PDF 在线预览分享链接
- 不承接 ToolKnit 的非 PDF 模块（音频转换、抠图、计算器、剪贴板、硬件检测等 39 个）
- 不做移动端 / macOS / Linux 首发版本（架构保留可移植性，但本期只交付 Windows）

## 2. 角色与使用场景

| 角色 | 能力边界 | 典型场景 |
|---|---|---|
| 普通用户（单机单实例） | 全部 107 项，无权限分级 | 合并合同、压缩扫描件、加水印、拆页 |
| 高级用户 | 额外可见「流水线」「脚本化批处理」「命令行参数」 | 批量给 200 份 PDF 加书签+页码+压缩 |
| 企业内网部署者 | 只做静默安装、指定数据目录、关闭遥测 | 内网 50 台机器统一分发 |

**权限模型**：单机单用户，**无登录、无角色鉴权**。唯一的「权限」是文件系统权限 —— 程序只读写用户显式选择的路径 + 自身数据目录，不碰其他位置。

> 需求缺陷预警：原始需求未提「多用户/共享电脑」。若后续要支持多用户共用一台机器，任务历史与配置需按 Windows 账户隔离（`%LOCALAPPDATA%` 天然隔离，已预留）。

### 3.2 去重结果：107 项独立能力

```
Stirling 99 项（全保留）
```

## 4. 【逻辑与状态机】

### 4.1 任务生命周期（核心对象：Job）

```
        ┌──────────┐  用户点「开始」   ┌────────┐  获取执行槽   ┌─────────┐
        │  Idle    ├─────────────────►│ Queued ├──────────────►│ Running │
        └──────────┘                  └───┬────┘               └────┬────┘
             ▲                            │ 取消                  │
             │                            ▼                      │
             │                       ┌──────────┐                 │
             │                       │ Canceled │◄────────────────┤ 用户取消
             │                       └──────────┘                 │
             │                                                    ├──► Succeeded（产物落盘）
             └──────── 重置/新任务 ──────────────┐                 │
                                                 │                 └──► Failed（错误码+日志）
                                            ┌────▼─────┐
                                            │  Result  │
                                            └──────────┘
```

**状态约束（强制）**：
- `Queued → Running` 必须有执行槽（并发上限默认 2，可配 1–4）
- `Running → Canceled` 仅在可中断点生效（PDFBox 长循环需注入 `CancellationChecker`；不允许"假取消"）
- `Succeeded` 必须持有至少 1 个产物文件，否则降级为 `Failed(code=EMPTY_OUTPUT)`
- 任何状态下进程崩溃，重启后 `Running` 一律回滚为 `Failed(code=CRASHED)`，产物目录标记 `orphan` 供清理，**不得静默续跑**

### 4.2 文件生命周期

```
选择源文件（只读引用，不复制）→ 校验（魔数 %PDF- + 可解析性）
  → 任务执行（中间产物写 %LOCALAPPDATA%\PdfKit\jobs\<uuid>\）
  → 用户「保存为」→ 目标路径写入（原子写：先 .part 再 rename）
  → 任务结束 N 天后清理中间产物（默认 7 天，可配）
```

**关键规则**：
- **绝不覆盖源文件**：若用户目标路径 == 源路径，强制改名 `原名_已处理.pdf` 并提示
- 源文件全程只读打开，不获取写锁（允许其他程序同时打开）
- 中间产物目录必须在系统盘外可配（避免 C 盘爆满）

### 5.1 Office → PDF 依赖策略（D-4 已定：调系统 Office）

| 方案 | 实现 | 安装包增量 | 结论 |
|---|---|---|---|
| **A. 调系统 Office（已选定）** | JNA 调 Word/Excel COM，`ExportAsFixedFormat` 导出 | **0** | ✅ 采用 |
| B. 内置 LibreOffice | 打包 soffice 便携版 | +350 MB | ❌ 否决（体积失控） |
| C. 首次运行按需下载 | 检测缺失时引导下载 | 0 | ❌ 否决（破坏离线承诺） |

**A 方案的实现约束（写入设计约束，不可简化）**：

| 约束 | 说明 |
|---|---|
| 位数必须匹配 | 64 位 JVM 只能调 64 位 Office。启动时探测注册表 `HKLM\SOFTWARE\Classes\Word.Application` 的 `LocalServer32` 路径，位数不符时明确提示而非崩溃 |
| 必须以可见/隐藏方式启动 | 用 `Dispatch.put("Visible", false)`，并 `Quit()` + `Release()`；异常路径也要在 `finally` 中退出进程，**严禁遗留 WINWORD.EXE 僵尸进程** |
| 支持格式 | `.doc/.docx/.xls/.xlsx/.ppt/.pptx/.rtf/.odt` 转 PDF；其余格式提示不支持 |
| 无 Office 时 | 检测不到 → 该能力置灰并提示「需安装 Microsoft Office；或先用其他工具转成 PDF」，**不得静默失败** |
| 并发 | Office COM 非线程安全，Office 转 PDF **独占串行执行**（即使队列并发为 2），并加全局锁 |
| 超时 | 单文件 120 s，超时强制 `taskkill /IM WINWORD.EXE` 并报错 |

## 6. 架构方案选型

### 6.1 三方案对比

| 维度 | A. 内嵌 Spring Boot + WebView | B. 纯 JavaFX 重写 | C. 混合内核 |
|---|---|---|---|
| 复用 Stirling 99 项 | 直接可用 | 需剥离 Spring 重写 | 剥离后复用 service |
| 安装包体积 | ~320 MB | ~150 MB | ~170 MB |
| 冷启动（P95） | 8–15 s | 2–4 s | 3–5 s |
| 峰值内存 | 600–900 MB | 300–450 MB | 400–600 MB |
| 开发工作量 | 最低（≈100 人日） | 最高（≈150 人日） | 中（≈110 人日） |
| UI 灵活度 | 高（Web 技术） | 中（JavaFX） | 高 |
| 长期维护 | 差（Spring 版本绑定） | 好 | 好 |
| 主要风险 | 冷启动被用户感知为"卡" | 99 项 UI 全重做 | 内核 API 需自设计 |
| **本项目** | **✅ 已选定（D-3，首发）** | ❌ 否决 | 🎯 终态目标（v2.0） |

### 6.2 已定路线：**A 起步 → C 收敛**

> D-3 已拍板：先用 A 拿到能双击运行的成品，再按 C 的模块边界逐步瘦身。**不重做 UI**，只换容器。

**阶段一：内嵌 Stirling 出包（3 周，M0–M2）**

| 步骤 | 动作 | 验收 |
|---|---|---|
| 1 | 装 Temurin JDK 25 + WiX 3.14 + Gradle 8；建 `pdfkit` 多模块骨架 | `gradlew build` 通过，`jpackage` 能出 app-image |
| 2 | 以 `app/core` + `app/common` 为依赖引入 Stirling（排除 `proprietary`/`saas`），改造成可内嵌启动（关闭 profile 校验、关掉不需要的 Bean） | 单体进程内能调用任一 PDF service |
| 3 | 内嵌 Jetty 监听 `127.0.0.1:<随机端口>`（不用 8080，避免冲突），窗口用 WebView 加载本地页面 | 双击 exe 出窗口，端口随机且不冲突 |
| 4 | 启动闪屏 + 后台初始化引擎（先出窗口再加载 Spring），并发上限 2 的任务队列落地 | 冷启动感知 ≤5 s（闪屏可见即算"已打开"） |
| 5 | 60 项能力挂到注册表 + 界面绑定 | 清点 60 项全可点、全可用 |

**阶段二：瘦身到 C（v2.0，首发后评估）**

- 用自研轻量容器替换 `@Service`/`@Autowired`，逐步摘掉 Spring 依赖
- 内核抽为 `core-engine` 纯 Java 模块，UI 与内核通过接口解耦
- 目标：体积 ≤170 MB、冷启动 ≤4 s、内存 ≤600 MB
- **前置条件**：阶段一已上线且稳定运行 1 个月，否则不做

### 6.3 推荐技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **JDK 25 (LTS, Temurin)** | Stirling 要求 `modernJavaVersion=25`；JDK 25 支持 jpackage/jlink |
| UI | **WebView2（JCEF/Edge WebView2）+ 本地 HTML**（首发）；JavaFX 21 为 v2 候选 | 首发复用现有 `pdf-hub` 前端，省 15 人日；JavaFX 待瘦身阶段再评估 |
| PDF 内核 | **Apache PDFBox 3.x**（Apache 2.0） | 唯一无传染性风险的全能库 |
| 加密/签名 | BouncyCastle + PDFBox 签名 API | 与 Stirling 一致 |
| OCR | Tess4J + tessdata（chi_sim + eng） | Apache 2.0；中文包 ~45 MB |
| 压缩包 | commons-compress / 7-Zip-JBinding | CBZ/CBR/EPUB |
| Word 输出 | docx4j 或 Apache POI | 仅 PDF→Word 用 |
| 表格 | Apache POI | Excel 表单导出 |
| 打包 | **jpackage**（`--type exe` + `--type app-image`） | JDK 自带；`exe` 类型需 WiX Toolset 3.x |
| 构建 | Gradle 8.x（Kotlin DSL）+ 多模块 | 与 Stirling 一致，便于拉取源码 |
| 测试 | JUnit 5 + TestFX（UI）+ 自建 PDF 样本库 | — |

**明确排除的库**：
- ❌ **iText 8**（AGPL，会把整个项目拖入 AGPL）
- ❌ **Aspose/PDFTron**（商业授权，费用高）
- ✅ 若确需 iText 高级功能，用 **OpenPDF**（LGPL/MPL）替代

### 6.4 模块划分

```
pdfkit/
├── app-ui/          JavaFX 界面、任务面板、11 个功能域页面
├── core-engine/     纯 Java，无 UI 无 Spring：107 项能力的执行入口
│   ├── analyze/ organize/ edit/ convert/ security/ bookmark/ filter/ optimize/ form/ pipeline/
├── core-model/      领域模型：Job、Capability、ConversionSpec、产物描述
├── core-runtime/    任务队列、并发槽、取消令牌、产物管理、日志
├── integration-stirling/  从 Stirling 抽取/适配的 service（唯一允许 Spring 残留的隔离层）
├── packaging/       jpackage 配置、WiX 模板、jlink 模块清单
└── tests/           样本 PDF 库 + 回归基线
```

**依赖方向强制单向**：`app-ui → core-engine → core-model`，`core-runtime` 被 engine 依赖但反向禁止。`integration-stirling` 只被 `core-engine` 通过接口调用，**不允许 app-ui 直接依赖**。
